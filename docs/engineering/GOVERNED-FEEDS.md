# Governed PostgreSQL snapshot feeds

Task APL-3026 · DDE-01–04 · C2 development · Owner authorized this connector on 21 October 2026. This is an opt-in candidate, not a production integration or accepted release. Existing AI/NocoDB REST context, AI grants and budgets are unchanged.

## Source and delegation contract

An operator privately configures `FEEDS_ENABLED=true`, absolute `FEEDS_SOURCES_FILE` and `FEEDS_STATE_FILE`, `FEEDS_DATABASE_URL` and a separate `FEEDS_NOCODB_TOKEN` metadata API token. No defaults connect a database or publish a feed. Keep mappings, credentials, state, WAL and backups outside the checkout/public web root with directory mode 0700, file mode 0600 and the app service account as owner. Include this new SQLite file/WAL in a separately qualified stopped-service backup plan before activation; the existing budget recovery drill does not qualify feed recovery. Do not put credentials into URLs sent to consumers, shell arguments, logs, Git or audit history.

The source file is a JSON array validated by `sidecar/lib/feeds/contracts.ts`. Each entry has `id`, `baseId`, `tableId`, `policyVersion`, SQL `schema`, `view`, stable unique non-null `key`, `delegation: "verified-full-base-admin-only"`, an actual `reviewRef`, `viewDefinitionHash`, and `fields`. Each field has stable NocoDB `id`, physical SQL `column`, approved display `title`, native primitive `uidt`, and `pgType` matching information_schema.data_type. No mapping or fictional review reference is shipped. Obtain the definition fingerprint with SHA-256 of the exact UTF-8 value returned by `pg_get_viewdef(view_oid, true)` on the intended PostgreSQL version. Review the actual view SQL, owner, dependencies, column/key mapping and security/RLS behavior; the hash detects later definition drift but cannot prove the initial review was correct. A database or NocoDB upgrade requires renewed mapping verification.

The NocoDB metadata token may carry broader permissions through its native role; keep it private and least-privileged for the supported version. This code issues only metadata GETs and does not claim that NocoDB enforces a metadata-only token scope.

Use a dedicated NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE LOGIN role, no ownership/membership in privileged roles, and SELECT only on the approved views plus USAGE on their schema. Do not grant base-table or NocoDB metadata access, schema creation or writes. Restrict CONNECT, PUBLIC grants and function execution as appropriate to the actual database. The connector verifies its view SELECT/no-write privilege, definition fingerprint, and non-superuser/non-bypass-RLS role; it cannot establish all transitive permissions/role memberships or the truth of a tenant policy. Operator review and negative database tests remain required. A read-only transaction is defense in depth; never use an owner connection string. TLS must verify the server for remote connections; no code disables certificate verification. Use the trusted private Docker network only for a same-host connection; never expose PostgreSQL publicly.

Only a current full-base owner or creator can create/manage a grant, and the accountable owner must be its creating user. Source table/base identity, live membership and approved field identity/name/type are checked using the separate native metadata credential. Consumer pages recheck owner membership and view availability/definition on every request; failure denies access. Restricted row/field delegation models are unsupported: do not configure a mapping for a base with finer permissions that cannot be verified by this contract. The operator-reviewed view can further narrow rows/fields. Direct SQL must not silently widen NocoDB permissions. Actual deployment mapping remains a release prerequisite, not a decision inferred from a passing synthetic fixture.

## Administrator flow

Open `/feeds` from the workspace. Select an approved workspace/table mapping, explicit primitive fields, named consumer, your accountable owner identity and expiry within 30 days. Explicitly confirm all rows or choose an equals-any filter on a projected field; the API also supports a bounded set of string/null values. SQL parameters carry values; identifiers only come from the reviewed mapping. An omitted scope fails validation. Linked, lookup, formula, JSON, attachment and unsupported fields fail closed, without implicit nested expansion. Source sessions pin UTC, ISO/YMD date style and PostgreSQL round-trip float formatting. Values are UTF-8 text or null, including numeric/date/boolean source fields, avoiding floating-point coercion; field metadata retains native and SQL types. Keys are feed-scoped HMACs of the source key, never hidden raw identifiers. Selecting a source-key column for disclosure must be an explicit field approval.

Creation returns a paused grant and a 256-bit read-only consumer credential shown once in the authenticated response. Only its SHA-256 digest is retained; a separate private per-feed seed signs cursors and opaque keys. Copy the credential into the named consumer's private secret store. Build a complete snapshot and inspect its manifest plus the first ten projected records, explicitly labelled as a preview. Resume only after a complete current snapshot exists. A new schema/source mapping or narrowed scope requires a newly approved grant; do not mutate an existing grant to reuse a consumer's prior approval. Newly added source fields are not automatically selected. Schema drift pauses existing reads and records a machine-readable fingerprint, affected safe field identities and reapproval reason. Existing schema metadata is retained as the last approved version; a new grant gets the new schema fingerprint.

Pause/resume is reversible until expiry/revocation. Revocation is permanent. Rotation atomically invalidates the old credential and cursor generation, pauses the grant and requires a fresh snapshot before resume. Browser controls disclose that access stops future requests; copies already exported cannot be recalled. A request admitted before a committed transition may finish; later admission rechecks lifecycle/generation immediately before response construction. Source permissions are checked at each request boundary, not continuously while bytes are in flight.

## Consumer protocol

Use HTTPS GET `/api/feeds/export?feed=FEED_ID&snapshot=SNAPSHOT_ID` with `Authorization: Bearer CREDENTIAL`; those uppercase identifiers describe response values, not configuration defaults. A normal UI cookie is insufficient. Only feed, snapshot, cursor and before parameters are accepted; arbitrary fields/scope and repeated parameters are rejected. Do not use query strings for credentials. Responses use no-store/no-referrer and expose no CORS allowance. No consumer writes are implemented.

A page has `manifest`, `mode`, `records`, `next`, `pageComplete` and `completion`. The first page always identifies a validated complete source extraction, but `completion` is null until the last page has been delivered. Follow `next` by requesting feed plus cursor alone. Retrying a cursor produces the same rows/versions while current access remains valid. The signed cursor binds feed/consumer generation, immutable snapshot, approved schema, offset, mode and expiry. It cannot switch snapshots. An unavailable, expired or incompatible snapshot/checkpoint returns 409 with a restart/resnapshot requirement. All denial/error responses omit source row content and credentials.

Manifests identify feed policy, snapshot/schema IDs, extraction start time, count, consistency and content digest. Extraction runs a PostgreSQL REPEATABLE READ READ ONLY transaction on one client, using a cursor fetching ten source rows at a time. Persisted staging rows are never consumable and do not count as a previewable/resumable snapshot. Failure/cancellation removes staging state and issues no complete manifest. Source identity and permissions are rechecked before publication. Pages read immutable protected SQLite records; PostgreSQL concurrent changes are visible only in a later snapshot.

Digest canonicalization is `dde-json-sorted-v1-newline`: recursively sort object keys by JavaScript lexical comparison, preserve array order, encode compact JSON UTF-8, append one newline for each full `{key,version,values}` record, SHA-256 the ordered bytes. The ordering is source-key text with PostgreSQL C collation, not opaque-key order. Record version is SHA-256 of canonical approved values; it denotes content state, not a database transaction sequence or every intervening write. The manifest digest can be independently recomputed across returned row pages.

For state changes, supply target `snapshot` and prior `before` snapshot. Both must be retained, authorized and from this same feed/generation/schema; the prior extraction timestamp must precede the target. This is a deterministic versioned state comparison, not an event stream: intervening edits that cancel each other are not events. Upserts contain the current approved row; removals contain only the already-approved feed-scoped opaque key and deterministic removal version (SHA-256 of canonical kind, key and prior approved content version, independent of extraction/delivery IDs). No old payload is included. Changes are sorted by opaque key with binary collation and paginated with mode-bound signed cursors. Missing/out-of-order checkpoints require resnapshot; source/policy permission loss yields denial rather than historical data. New consumer grants/rotations cannot read older-generation history. The completion manifest/digest describe the target dataset, not a digest/count of only changed rows. Apply changes idempotently by feed, key, version; checkpoints use the exact snapshot pair and next cursor.

## Limits, audit and verification

At most 64 lifetime grants per state store, two retained snapshots per feed, 24-hour snapshot TTL bounded by grant expiry, 25,000 rows and 16 MB canonical records per complete extraction, 8,192 UTF-8 bytes per projected field, 100 records per consumer page, two concurrent snapshot builds and four concurrent HTTP feed operations. SQL statements/connects have deadlines and extraction has a 45-second overall connection cutoff. These are conservative implementation limits, not a 50-user capacity promise. Oversize operations fail explicitly; there is no successful silent truncation. Private SQLite storage is capped at 65,536 pages; exhaustion fails operations, including audit, rather than granting access. Secure storage retention/rotation and a deployment-specific sizing/backup plan are required before use.

Access/lifecycle history is restricted to authorized full-base administrators. It records consumer/actor, server time, action/outcome, policy/schema/snapshot identity and bounded count/digest/range evidence, without rows, filter values, credentials or cursor secrets. `success` for a page means admitted for response delivery, not confirmed receipt by the downstream consumer; network cancellation after admission cannot be recalled. Build failures/interruption are recorded where storage remains available. Audit write failure refuses the operation; successful lifecycle changes, snapshot publication and page admissions are transactional with their audit event. Older than the last 10,000 events globally is unavailable; history reports its retention boundary/gap rather than claiming a complete permanent ledger. Protect/monitor/archive the state independently if a longer audit requirement is approved.

Unit regression tests cover explicit grants, cross-feed credentials, tampering/retry, exact/empty boundaries, immutable snapshots, staging/resume race, pause/expiry/revoke/rotation, source denial, deterministic changes/gaps and fail-closed audit. CI exercises synthetic native PostgreSQL/NocoDB mappings and the compiled API. Actual production mappings, complete field/row delegation semantics, independent native acceptance, host workload and feed-state recovery remain separately required. Never infer deployment approval from engineering test success.

Sources: [PostgreSQL repeatable-read semantics](https://www.postgresql.org/docs/17/transaction-iso.html) and [node-postgres transaction client requirements](https://node-postgres.com/features/transactions).
